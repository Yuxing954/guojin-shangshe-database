# WORK 纪要每小时同步

来源为本机 `D:\WORK\纪要`，递归检查正式纪要和压缩包内文档，排除“数据库”目录、Word 临时文件。2026-10-09 用户要求提取标题、日期、公司、主题、正文和来源并同步至本仓库，因此本流程将真实提取正文保存在 `data/research/processed/`；与原有默认只登记 OneDrive 原件的流程分开。原件保持原位置，不创建云端公开分享权限。

每小时由本聊天的定时任务执行，GitHub 读写均使用已连接的 GitHub 连接器。电脑须在线、应用须运行。现有 GitHub Actions 只构建仓库摘要与资源索引，不扫描本地文件；它不能代替这个任务。

## 准备和验证

1. 读取 main 的最新提交、目录、`data/research/library.json` 与已存在的 processed 文档。保留原有记录、人工摘要、审阅状态、日期疑点和有效下载入口。
2. 将当前仓库基线放入隔离的本地工作目录。私有状态和日志留在仓库外，不提交认证信息、绝对本地路径或云端权限回执。
3. 运行 `python scripts/sync_work_minutes.py --source-dir "D:\WORK\纪要" --private-dir <私有状态目录> --root <仓库基线目录>`。该步骤仅准备本地文件，输出 `pending.json` 与追加的 `runs.jsonl`，不表示发布成功。
4. 按文件 SHA-256、正文规范化指纹去重。已有同一文件补充正文；内容更新沿用记录身份，清除失效的旧版本摘要和下载绑定。改名、复制与压缩包重复不新增记录。原件删除不自动删除历史记录。
5. 提取 Word 正文段落和表格；PDF只读取真实文字层并保留页码；UTF-8文本原样读取。扫描件、旧版Word、音频、损坏或正在变化的文件记录失败，后续重试，不能从文件名推断正文。正文中表格以单元格段落顺序保存，不声称保留视觉版式、图片或页码。
6. 日期区分文件名日期、原文日期和修改时间；疑点保持待核对。公司优先使用已有核对字段或标题明确出现的名称，缺失留空，不从行业名虚构公司。主题采用去掉文件名日期和扩展名后的原始名称。每篇正文保存来源文件名、相对位置和原件哈希。
7. 通过 GitHub 连接器构造包含本批变更的树和单个提交。在写入前检查受影响文件的基线，使用预期分支头更新 main，不能强推。并发冲突时重新读取、重新准备，不能覆盖别人的更新。
8. 回读所有变更文件并逐项比较实际内容哈希、记录数量、正文引用和资源目录。仅在回读一致后写入私有 `verification.json`（实际 commit、verified=true、逐文件SHA-256），再运行 `python scripts/sync_work_minutes.py --ack --private-dir <私有状态目录> --root <仓库基线目录> --commit <实际提交> --verification <核验回执>`。

后续每次全量比较文件哈希，避免因旧修改时间或同秒修改遗漏新增内容；按逐文件成功记录推进检查点。失败项不推进。没有变化不提交。网络、权限、构建、来源读取失败追加日志并报告原因；不能把准备完成、提交创建或构建触发当作最终同步成功。

网站保留原文前500字预览。新提取正文可进入纪要列表与公司搜索；原件未开放下载时显示“下载未开放”，不伪造 OneDrive 下载链接。完整正文已在公开仓库中按用户本次要求同步。

## 验证

`python -m unittest discover -s scripts -p test_work_minutes.py` 覆盖重复文件、压缩包重复、失败重试、版本更新、未核验不得推进状态、保留已有摘要和日期疑点；`node scripts/research-library-model.test.cjs` 覆盖文字可用性与下载权限的独立判断。
